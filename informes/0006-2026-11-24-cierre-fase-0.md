## Decisiones

### Framework de interfaz: Svelte 5 + Vite (aprobado por el responsable del proyecto)
Lo que más pesa en un gestor de contraseñas:
- Cuánto código de terceros entra (riesgo de la cadena de suministro).
- Que sea difícil introducir fallos de inyección de código (XSS).
- Que la interfaz del MVP se pueda construir con poco código.

| Opción | Valoración |
|---|---|
| TypeScript sin framework | Mínimas dependencias, pero mucho código propio y la protección contra XSS depende de la disciplina. Alternativa si algún día se quisiera cero dependencias. |
| **Svelte 5** | **Elegido.** Se compila y apenas añade código a la app. Protege contra XSS por defecto (insertar HTML exige `{@html}`, que se ve en revisión). Es el más rápido de escribir para listas y formularios, tiene plantilla oficial de Tauri 2 y sirve también para la extensión. |
| SolidJS | Técnicamente muy bueno, pero con menos comunidad y fácil de usar mal si se programa como en React. |
| Preact | Buena opción si el equipo ya sabe React; si no, no aporta nada frente a Svelte. |
| React | Descartado (ver abajo). |

**Por qué no SvelteKit:** añade rutas, renderizado en servidor y más dependencias que una app de escritorio local no necesita.

**Por qué se descartó React:**
1. **Más código de terceros.** `react` + `react-dom` añaden bastante más código a la app que Svelte. Y lo más importante: el ecosistema empuja a sumar paquetes para cosas básicas (formularios, estado, rutas). Cada paquete de npm es una puerta para un ataque a la cadena de suministro, que es justo el riesgo que más importa en un gestor de contraseñas.
2. **No aporta seguridad extra.** React también escapa el HTML por defecto (`dangerouslySetInnerHTML` es el equivalente a `{@html}`). En XSS empata con Svelte, pero no lo mejora.
3. **Más complejidad para la misma interfaz.** El DOM virtual, los hooks y las reglas de dependencias de `useEffect` son una fuente habitual de errores. Para una interfaz pequeña (lista, búsqueda, formulario, generador, ajustes) es complejidad que no se aprovecha.
4. **Su ventaja principal no aplica aquí.** Las grandes ventajas de React son un ecosistema enorme y lo fácil que es encontrar desarrolladores. En un proyecto interno con una interfaz pequeña y la consigna de usar las mínimas dependencias, el ecosistema es más un riesgo que una ayuda.

Si el equipo ya dominara React, la opción razonable habría sido **Preact**: misma forma de programar y mucho menos código.

### Otras
- **cargo-deny sin acciones de terceros:** se instala con `cargo install` (desde crates.io, versión fija) en lugar de usar la acción `EmbarkStudios/cargo-deny-action`. Así solo se ejecuta código de GitHub y de crates.io. La caché evita reinstalarlo en cada ejecución.
- **Lista de licencias mínima.** Cuando entre Tauri seguramente habrá que añadir alguna; se hará en ese cambio.
